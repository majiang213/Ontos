# 提示词审计 —— 判据 / 形状 / 契约

注：LLM 接入层已于 2026-08-29 更名（接口与实现名见 ADR 0009）；文中行号对应**更名前版本**。2026-08-30 唯一键判定落地（ADR 0010，新增 `proposeKey` 出口、identityHint 判据与召回分家）后行号再漂一次；本文的判据结论仍有效，行号以现行代码为准。

范围：`src/server/infra/llm/` 全部提示词面——真模型五条（`aiSdk.ts`：nlToQuery / proposeObjects / proposePairs / proposePair / proposeKey（ADR 0010 新增））、离线演示实现的启发式（`demo.ts`）、规则单源（`identityHint.ts`——判据 `IDENTITY_COL_RULE` + 召回特征 `KEY_HINT_NAME_RE` / `KEY_HINT_DESC_RE`、`llm.ts`）。判「形状还是判据」的依据是接口产出的消费方：出接口 Zod、`schema/verdict.ts`、`schema/config.ts`、`features/ontology/validate.ts`、`features/integrate/`、`features/ontology/stages.ts` 与 `skeletons.ts`、`features/acceptance/`、根目录 `CONTEXT.md`。只读代码，未跑应用与测试，未改任何源码。

三档口径：

- **判据**：说清「什么答案算对」，能对照现实或配置检验。
- **形状**：把某份数据（演示库）的表面模式当判据——列名前后缀、写死的枚举值、写死的领域名词、写死的演示数值。
- **契约**：输出形状与语法约束（JSON Schema、枚举键集合、命名约定），与引擎/校验的硬约束一致。

## 结论摘要

已修 3 条（发现①此前已修；发现②③于 2026-08-29 按 ADR 0008 修完），豁免 10 处：

1. **发现①（已修）**：`identityHint.ts` 曾把「identity 选 `_no`/`_id` 结尾的列」当判据——列名形状证明不了唯一；现行文本已改成「跨源能对上同一个体的业务编号列」。
2. **发现②（已修）**：两条整合顾问提示词把时期名写死成「设备 in_transit / in_service，人 candidate / employed」，演示实现对所有对硬编码设备词，引擎兜底 `executionPlan` 同病。现已按 ADR 0008：时期名判据改为「原样取自建议输入里现成枚举值域的取值」，兜底单源 `executionPlan` 用中性占位 early/late（中文名 早期/晚期），`applyVerdict` 自备兜底退役，裁决卡显示将落地的词。
3. **发现③（已修）**：演示实现不再产时期名、不猜谁早谁晚；`STAGE_FIELD` 状态类列名只当列表层召回偏置，不是生命周期判据。
4. nlToQuery 与 proposeObjects（修①之后）没有形状病：前者是契约加判据，后者的规则逐条对得上引擎硬约束。

## 发现明细

### 发现①（已修）identity 把列名前后缀当判据 —— 格式示例

- **位置**：`src/server/infra/llm/identityHint.ts:9-15`（现行文本）。
- **原规则**：「identity 选业务编号列（_no/_id 结尾优先）」。
- **为什么是形状**：`po_id` / `dev_id` 这类自增代理主键同样以 `_id` 结尾；演示库 9 张表里 5 张被建议了跨源对不上号的键。列名后缀是某份数据的表面模式，不是「能区分、能覆盖、稳定」的判据（CONTEXT「同一性标准」）。
- **为什么这条必须是判据**：建议错键不会被任何闸拦下——交集率按 identity 列取值算集合重合（`integrate/overlap.ts:46-53` 经 `keyColumn`），错键只会算出无效命中；发布闸只查「每个源条目有对齐属性」（`validate.ts:31-38` `cfgNoRowKey`），不查键选得对不对。防线只能设在判据本身。（2026-08-30 起识别有第二道防线：数据试算 + 人确认，见 ADR 0010。）
- **现行判据版**（原文引用）：「identity（唯一键）选跨源能对上同一个体的业务编号列：取值是业务发给个体的编号（序列号、单号、证件号这类），唯一且稳定；列名什么形状都可能，按列义与列注释判断，不要按 _no/_id 之类前后缀猜；列带 unique 标记（数据库唯一约束）是「唯一」的硬证据：非整数、语义是业务编号的唯一列直接当 identity；自增代理主键（整数 pk）只是表内行号，跨源对不上号，即使唯一也不能当 identity；多列主键、多列唯一索引的单列不唯一，不能当 identity（pk / unique 标记可能只是复合键的一员）；没有合格的列就省略 identity，留给人定」（`identityHint.ts:9-15`）。
- **影响面**：修复前，演示域之外任何含代理主键库表的逆向建模都会拿到跨源对不上号的唯一键建议，交集率全程命中为零，三问的第一问失真。

### 发现②（已修，ADR 0008）时期名写死「设备/人」两套；非演示域的生命周期裁决会落错词

- **位置与原文**：
  - 清单建议（`aiSdk.ts:168`）：「每对都必须写 keep……和 stage.earlier / stage.from / stage.to（较早时期的类与英文小写时期名：设备用 in_transit / in_service，人用 candidate / employed）」。
  - 看过交集率的建议（`aiSdk.ts:201`）：「……必须写 keep……和 stage.earlier、stage.from、stage.to（时期名英文小写：设备 in_transit / in_service，人 candidate / employed）」。
  - 演示实现（`demo.ts:133-139`）：`withApplyPlan` 给**每一对**建议补 `stage: { earlier: pickEarlier(a, b), from: "in_transit", to: "in_service" }`——不分领域，连演示里的人对（候选人×员工）也拿设备词。
  - 引擎兜底同病（`schema/verdict.ts:67-68`）：`executionPlan` 在建议缺时期名时补 `"in_transit"` / `"in_service"`。
- **为什么是形状不是判据**：判据要能说「什么时期名算对」。这里「对」的唯一来源是演示库两个域恰好用的词（十二套演示库：`infra/demoSystems.ts:18-29`；设备值域：`src/server/config/ontology.yaml:24-27`）。演示词汇被写成了所有领域的规则。而且它连契约都算不上：引擎对时期名没有任何词汇约束，「英文小写」只活在提示词和注释里（`verdict.ts:46`「时期名（英文小写）」）——`transition.from/to` 允许任意字符串或数字（`schema/config.ts:165-171`），`edit_stages` 只查非空与去重（`ops/editStages.ts:63-64`）。佐证：真模型走查文档把「人对写成 in_transit / in_service」列为模型失败信号（`docs/真模型端到端测试.md:211-212`）——走查能过，只因提示词枚举的两套词恰好覆盖走查的两个演示域。
- **时期名落在配置哪里（链路）**：画布裁决时人只点关系类型，PairCard 把 `executionPlan(pair.class_a, pair.class_b, verdict, advice)` 算出的 `stage_names` 原样发给 `/api/decide`（`components/cards/PairCard.tsx:57-66`）→ `decide` → `adjudicate` → `applyVerdict`（`integrate/decide.ts:42`；`applyVerdict.ts:226-227`）。生命周期分支把时期名写进四处（`applyVerdict.ts:141-175`）：
  1. 合并类新增派生属性 `status` 的值域 `values: [from, to]`（157-159 行）；
  2. 同一属性 `derived` 规则的产出值（161-164 行）；
  3. 自环转化关系：关系名 `${a}_to_${to}`、反向名 `${a}_from_${from}`、`transition: { from, to }`（166-172 行）；
  4. 转化动作：名字 `convert_to_${to}`（`skeletons.ts:63-65`）、描述「转化为${to}」（`skeletons.ts:72`）。
  时期名**不进** `class_conclusions`（该表只收 overlap / homonym / subtype：`schema/config.ts:176-178`；生命周期分支没有 push）。写进配置后，画布阶段块、对象卡（键名原样显示：`src/tests/objectCard.test.ts:41`）、问数过滤字面量、动作前置全都消费这几个词。
- **引擎对时期名的约束（核查结论）**：结构层任意字符串/数字（`config.ts:165-171`；`values` 允许任意字面量，`config.ts:50-57`）；语义层只要求 transition 两端值落在派生规则产出集合里（`validate.ts:105-113`），而 `applyVerdict` 自己生成的 values 与 derived 恒满足，等于没约束；改标识（`edit_stages`）可事后级联改写关系名、反向名、transition 与转化动作（`ops/editStages.ts:68-105`；测试钉住该链路：`src/tests/ops.test.ts:99-114`）。
- **换成什么判据（方向）**：提示词侧把「时期名」从枚举词汇改成判据——「from/to 填这两个类各自领域里早、晚阶段的标识：优先从两类字段、枚举值、列注释里找现成的状态取值；找不到就留空」，删掉设备/人两套写死词（含 168 行括号里「候选人表和员工表」这类演示例子，换领域中性说法）。引擎侧把 `executionPlan` 的设备词兜底与 `applyVerdict` 的类名兜底（`${a}_前` / `${b}_后`，`applyVerdict.ts:142-143`）并成一处按类名派生——现在同一不变量有两个家、两套答案，画布路径（PairCard 恒带 stage_names）永远走设备词兜底。
- **影响面**：演示两域之外的一切生命周期裁决——订单（已提交→已履约）、工单（已受理→已关闭）、审批流、会员状态。真模型下模型照抄提示词就把 in_transit/in_service 写进订单类：值域、派生规则、`order_to_in_service` 关系、`convert_to_in_service` 动作全套带设备词，此后「已履约订单多少」编不出能对上行数的查询（过滤值只能取 values 字面量，字面量是设备词）；模型自造词则偏离提示词，产出失去依据（零温度加固定种子保证同一输入产出稳定——`aiSdk.ts:45-47`——但稳定不等于正确）。演示实现下所有对一律设备词，连演示世界的人对都要人事后用改标识救回（`ops.test.ts:99-114` 的级联改写就是这条修复链）。错词不是显示问题：人点完裁决按钮，错词即进工作副本，发布后问数与动作读的就是它。

### 发现③（已修，ADR 0008）演示实现把「列名带 status/state」当生命周期证据，把「哪侧没有状态字段」当时间序

- **位置与原文**：
  - `STAGE_FIELD = /status|state|阶段|状态/`（`demo.ts:108`）；`ownStage` / `hasStageField`（110-116 行）。
  - 倾向：`ratio > 0.8 ? 类等价 : hasStage ? 生命周期 : 部分重叠`（152 行）；看过交集率后，「接近全交且有状态字段且第一版倾向生命周期 → 维持」（190-191 行）、「有交集又不是全交，又有状态字段 → 生命周期」（201 行）。
  - 时间序：`pickEarlier`——「只有一侧有状态字段时，没状态的更早」（127-131 行）。
- **为什么是形状不是判据**：「这一对是同一个体的不同时期」的判据在 CONTEXT 里写得很清楚——先得是对得上号的同一个体（第一问命中大于零是硬线索），状态只是第三问的线索。演示实现把「任一侧有个名字像状态的列」直接升格为生命周期倾向的独立依据，字段名的表面模式替代了同一个体判定。`pickEarlier` 更进一步：从「哪侧没有状态字段」推时间先后——这条规则在演示库成立是巧合（早阶段的采购源没有状态列，晚阶段的设备台账有），不是规律。同一文件对 identity 已经把话说透：「演示实现没有语义可读，不按列名形状猜识别字段（规则单源 identityHint：形状证明不了唯一，_no/_id 结尾同样可能是自增代理键）」（`demo.ts:52`）——同一份纪律没有贯彻到阶段识别。对照真模型提示词：「有状态字段」只与第一版倾向联合出现（`aiSdk.ts:200`），且明文「状态、日期只是线索」（195 行）——线索与判据的界限在提示词里守住了，演示实现越了线。
- **换成什么判据（方向）**：阶段倾向至少锚在硬信号上——两侧 identity 已定且交集命中大于零（对得上号是同一个体）才谈生命周期；谁早谁晚不猜形状：用已有的计数信号（交集率取数时哪侧的识别值在另一侧有对应）或留空交给人；时期名留空由引擎按类名兜底（见发现②）。
- **影响面**：演示实现模式（无模型 Key 的所有空间）里，两表字段重合过闸（≥40%，147 行）且任一侧有 status/state 类列名，就会被建议「生命周期」并附设备时期名与形状推出的先后——即使两类不是同一个体的两个时期（如供应商表与供应商联系人表共享地址字段和 status 列）。人按建议点「生命周期」，落进配置的就是发现②的错词加错序。
