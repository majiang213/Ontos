# 真模型走查（一家公司 · 三波接入 · 十二套源系统）

这是 Ontos 的可演示走查剧本：同一家公司，三条业务线（物、人、客与货），分三波接入十二套老系统。
操作者在画布里点完全部关卡——连接、勾表、生成对象、改唯一键、删字段、裁决、发布、跑问题集；
动作演示在画布外走 MCP。测试代码不代人点这些关卡（那是非目标，见文末）。

**走查必须配真模型三件套**（`OPENAI_API_KEY` / `OPENAI_BASE_URL` / `OPENAI_MODEL`）。不配也能起服务，
但离线回退只够证明「连得上、表在、列注释在」：候选对建议是通用启发式，问数剧本只覆盖 `test` 演示空间——
空白空间里的生成、裁决建议、问题集跑批都必须走真模型。

**两套世界，数字不要混。** `test` 空间是附录 C 模板 + 四个内存 fixture（在役 **97** / 在途 81 / 报废 3），
给 `engine.test.ts` 钉数字用。走查在**新建空白空间**里进行，设备阶段世界只有两条规则：
在役 **100**（设备源 100 行，含 3 台台账 scrapped）、在途 **81**（采购 121 − 重合 40）。
人同理：在职 **50**、仍停在候选人的 **50**。别拿 97 来卡走查。

## 0. 准备

```bash
export OPENAI_API_KEY="…"
export OPENAI_BASE_URL="https://api.x.ai/v1"   # 或任何 OpenAI 兼容端点；填基址，SDK 自己拼 /chat/completions
export OPENAI_MODEL="…"                        # 必须显式
# 不要设 ONTOS_TOKEN：浏览器写请求配不上令牌会 401
npm run dev    # http://localhost:6688
```

另开终端，仓库根：

```bash
npm run demo:seed
```

该看见：十二个系统的清单——给人看的名字、连接名、类型「SQLite 文件（演示）」、绝对路径。
文件写在 `.ontos-demo/`（不进 git），重复运行整份覆盖。**验收动作之后再播种会丢掉刚写回的设备行。**

播种只写文件：不动元库、不替你连任何空间。连接由你在画布表单里逐套接。

浏览器里：左上角下拉 → 「新建工作空间」→ 起个名字（如 `lab`，小写字母开头）。
**不要用 `test`**（已发布附录 C + 内存四连，看不见「接入」这一关）；
**不要假设 `default` 是空的**（本机玩过就可能残留旧连接）——新建一个。

**认对象靠来源标签，不赌类名。** 画布节点标题是模型起的类名（可能是 `po_item` 也可能是 `purchase_item`）；
节点下方的来源标签是 `连接名.表名`（如 `device_sys.device`）。下文「采购对象」= 来源标签含 `purchase_sys.po_item` 的那个节点。

## 1. 十二套系统（连接表单的答案）

`npm run demo:seed` 的 stdout 打印十二行连接答案，四列与下表对齐：给人看的名字、连接名、「SQLite 文件（演示）」、绝对路径（下表另两列——表、保存后 toast 表数——是接入后的核对项，不在 stdout）。连接名必须照填（来源标签靠它认对象）；类型选「SQLite 文件（演示）」；文件路径填打印出来的绝对路径。
连接表单默认是**下拉选择**：直接列出 `.ontos-demo/` 里的 .db 文件（带给人看的名字与建议连接名，已连的标「已连接」），勾选即连，连接名自动照清单填好；想核对或指定别处的文件，切「手动填路径」再照抄绝对路径。两种方式保存后 toast 表数必须与下表一致。

| 波 | 给人看的名字 | 连接名 | 表 | 保存后 toast 表数 |
|---|---|---|---|---|
| 1 物 | 采购系统 | `purchase_sys` | `po_item`、`order` | 2 |
| 1 物 | 设备台账 | `device_sys` | `device`、`department`、`assignment` | 3 |
| 1 物 | 资产系统 | `asset_sys` | `asset`、`warranty_card` | 2 |
| 1 物 | 维修工单 | `repair_sys` | `repair` | 1 |
| 1 物 | 点检系统 | `inspect_sys` | `instrument` | 1 |
| 2 人 | 招聘系统 | `recruit_sys` | `candidate` | 1 |
| 2 人 | 人事系统 | `hr_sys` | `person`、`appointment` | 2 |
| 2 人 | 办公账号 | `oa_sys` | `account` | 1 |
| 3 客货 | 客户档案 | `crm_sys` | `customer` | 1 |
| 3 客货 | 销售系统 | `sales_sys` | `customer`、`order` | 2 |
| 3 客货 | 仓库系统 | `wms_sys` | `stock` | 1 |
| 3 客货 | 应收发票 | `ar_sys` | `invoice` | 1 |

保存后 toast：`已连接 <连接名>，读到 N 张表`，并自动打开表结构抽屉。抽屉里每张表：列名 / 类型 / 主键 / 列注释，
列下面是最多 3 行脱敏采样（空表写「没有行」）。列注释来自库文件旁边的 `.comments.json`
（拷库不拷它时按文件名回退种子注释；它坏了会在保存时被表单拦下）。

若列注释缺失：停下来查 `.ontos-demo/<库>.comments.json` 是否存在，不要继续生成——字段说明会变差，唯一键更难认。

## 2. 第一波 · 物（5 个库）

### 2.1 接入，看抽屉

按 §1 接入 `purchase_sys` / `device_sys` / `asset_sys` / `repair_sys` / `inspect_sys`。抽屉里该看见：

- `purchase_sys.po_item`：列 `sn` 旁有「设备序列号」；采样能看到 `SN-4xxxx`（按插入顺序是 `SN-40000` 起，主角 `SN-40217` 是第 121 行，不要求出现在采样里）。
- `purchase_sys.order`：办公采购（打印纸、文具供应商），**没有**序列号——它是第三波的演员，这一波别勾。
- `device_sys.device`：列 `serial_no` 注释「设备序列号」、`status` 注释「台账状态」。**没有 `repair` 表**（维修独立成库了）。
- `asset_sys.asset`：采样处写「没有行」。0 行是正常的，不是接错了。
- `repair_sys.repair`：15 行工单，序列号来自在役设备；一条未结束。
- `inspect_sys.instrument`：60 台点检仪。

### 2.2 勾表，点「生成对象」

在抽屉勾选：`purchase_sys.po_item`（**不勾** `order`）、`device_sys.device`、`device_sys.department`、`asset_sys.asset`、`repair_sys.repair`、`inspect_sys.instrument`
（`assignment` / `warranty_card` 可选，多勾多几对候选，不挡主路径）。

点「生成对象（N 张表）」。该看见：toast「已生成对象：…（草稿，发布后生效）。点「待确认」定唯一键」；抽屉收起；
画布出现带来源标签的节点；字段说明吃到了列注释；每个新对象自带一条 `set_fields` 动作（对象卡「动作」区可见）。
耗时常见 5～30 秒。

失败：toast 是上游文案；模型调用的原始产出写在系统临时目录 `ontos-llm-fail/` 下（进程 stderr 打一行路径，密钥字面值已打码）。

### 2.3 人改关卡：唯一键与非派生 `status`

点工具条「**待确认**」，底中面板两段解锁：**①唯一键先定，②疑似重复才展开**（交集率、阶段配对都建在唯一键上，
键没定就裁会出「合法但错误」的关系——发布闸查不出字段选得对不对）。

①唯一键区块里，把 `purchase_sys.po_item` 和 `asset_sys.asset` 两行的下拉换成**对照了列 `sn`** 的那个字段
（选项文字是「字段名（列注释）」，认注释是「设备序列号」的那项；`device` / `instrument` 两行模型已选对 `serial_no`，
直接确认即可），点「**确认唯一键**」收口，②区块随即展开。想核对：再打开表结构抽屉，对应列的映射去向不再是「未映射」。
若仍是「未映射」：模型没把该列收进属性——删掉该对象重新生成，不要手写对照骗过发布闸。
点检与设备的名称属性如果同名（都叫 `name`），部分重叠会把 `name` 挪到公共对象上；不同名也能裁，公共对象只带唯一键。想让名称也成为公共字段，再在对象卡改成同名 `name`
（改名会把来源映射一起换过来，对照不断）。不要 ✕ 掉起错名的字段——画布没有拉列入对象，对照补不回来。

设备对象上的非派生 `status`（说明常是「台账状态」）：**必须在点「阶段」之前 ✕ 掉，推荐在点「同一」之前删。**
阶段裁决要立派生字段 `status`，撞名会被拒。点过「阶段」再删会撞派生 `status` 与转化关系的引用。
若模型把列 `status` 收成了别的属性名（如 `mark`），不要删——撞名的是属性名 `status`，不是列名。

维修对象唯一键用维修单号（对照了 `repair_no` 的字段），不要改成设备序列号。

**可选检查点**：唯一键改完、`status` 拿掉之后可以先点一次「发布」。后面裁反了再「放弃」，
回到的是**上次已发布**快照（对象还在），不是空画布。

### 2.4 按强制顺序裁（仍在「待确认」面板的②区块）

①确认后切到疑似重复，一次只出一对（LLM 建议只是软证据，硬证据是「算一算交集率」）。
同一库两张表也可以成对（`device` 与 `department` 都来自 `device_sys` 若出现，按三问裁，通常是仅名称相似，不是 bug）。

一次只出一对。点「同一」后选留下谁；点「阶段」后选谁更早，再填时期名。已经算过的交集率会按类名跟着走。

强制顺序（第一波）：

1. **设备 × 资产 → 同一**。点「同一」，留下设备、资产并进来。
   交集率 **0%** 也裁同一：资产表此刻没有行是功能不是故障——「同一」裁的是「同一类东西挂多个来源」，不是「两库现在就有同一批行」。
   成功信号：资产节点消失，设备对象来源标签变成两个。
2. **点检 × 设备 → 部分重叠**（同一之后、阶段之前，对着还没并进采购的设备类）。先「算一算」：
   应是 **40%**（100 条、60 条，其中 40 条对得上号）。若拖到阶段之后再算会变成约 22%（40/181）——那时停下来，顺序错了。
   点「部分重叠」。成功信号：画布多一个公共对象（类名形如 `shared_*`），点检与设备两个原类都还在，序列号仍在各自类上。
3. **采购 × 已合并设备 → 阶段**。点「阶段」，早的选采购、晚的选已合并设备。阶段名填早 `in_transit`、晚 `in_service`
   （输入框示例就是这两个英文；问数按这里填的字过滤，不要填「在途」「在役」）。
   成功信号：toast 提到加了状态字段和「转为 in_service」动作。
4. **阶段之后新出的「点检 × 采购合并类」**：点「跳过」或「仅名称相似」。禁止同一 / 阶段（再并一次会把 100/81 翻掉）。
5. **维修 × 设备（若出现）**：仅名称相似或跳过。维修是事件不是设备。这两种结论不弹 toast，条目从面板消失即是反馈。

各对交集率参考：采购 × 设备约 33%（40/121）；设备 × 资产 0%；点检 × 设备 40%（必须在阶段之前算）。

### 2.5 发布

工具条「发布 vN+1」。toast「已发布 vN，问数与动作即刻生效」。422 就是校验文案，照着改，不要改 YAML 硬过闸。
发布后合并类上应有派生 `status`（两条规则）与动作 `convert_to_in_service`（对象卡「动作」区可见）。

### 2.6 问题集关卡（全绿才能进第二波）

工具条「验收问题集」：

1. 点「**换成第一波问题**」——会先清空本空间全部题（含手打的）再装入，**不自动跑**。
   toast「已换成 4 条第一波问题」，列表立刻出现四条，每条旁边标着期望数字（100 / 81 / 1 / 15）。
   看不见期望数字就停下来，不要先跑。
2. 卡上那行说明：「这是空白空间走完这一波裁决后的数字，不要在 test 空间用。」
3. 点「**全量跑一遍**」。每条变成「通过」或「失败」，失败的那条旁边留下本次明细
   （「期望合计 100，实得 0」「编译失败：…」这类）。点状态标签看全文。
4. **全绿才能离开第一波。** 红了看明细，回画布改（唯一键、阶段名、误裁），再发布，再跑。

第一波期望：

| 问句 | 期望 | 含义 |
|---|---|---|
| 在役设备一共多少台 | `100` | 合并设备类（来源标签含 `device_sys.device`）上 `status = in_service` 的行数；含 3 台台账 scrapped |
| 在途设备一共多少台 | `81` | 121 − 40 |
| 序列号 SN-40217 且处于在途阶段的设备有多少台 | `1` | 主角还在采购源、不在设备源 |
| 维修工单有多少条 | `15` | 独立库 15 行；误裁同一这条会红 |

问数若走聚合：过滤已钉阶段时按 `status` 分组，合计列名是引擎产出的（`count` / `count_status`），对错板比的就是合计。
显式 `limit` 比期望小会直接记失败（截断了没法比）。

### 2.7 画布外验收一台（可选，也可放到三波之后）

动作不进站内 UI。外部 Agent 用 `skills/ontos-action-run`，或 curl。路径段填**你的走查空间名**：

```bash
curl -s "http://localhost:6688/api/lab/mcp" \
  -H "Content-Type: application/json" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"run_action","arguments":{"action":"convert_to_in_service","object":"<合并类名>","identity":"SN-40217"}}}'
```

MCP 约定 HTTP 一律 200，业务结果在信封里：成功看 **`result.structuredContent`**——`ok: true`，
`projections` 里至少有一条对 `device` 表的成功 `insert`（给没有这行、又映射了识别字段的源插行；资产源通常也插一行）。
动作名以对象卡为准：`convert_to_<晚阶段>`。附录 C 模板里的 `convert` 只属于 `test` 空间，别抄。

验收动作成功后，回「验收问题集」：点「**换成验收后问题**」再「全量跑一遍」——
期望从 100 / 81 翻成 **101 / 80**（SN-40217 在役 1 条、在途 0 条）。全绿才算这一拍结束：
动作改的是源库文件，问数读的是同一份文件。

## 3. 第二波 · 人（3 个库）

### 3.1 接入，只生成新表

接入 `recruit_sys` / `hr_sys` / `oa_sys`（toast 表数 1 / 2 / 1）。抽屉里：

- 招聘 `candidate` 采样：姓名明文；`mobile` 脱敏成头尾（老系统的脏号——`+86 138-…` 这类，归一化规则洗得回来）；`id_no` 不脱敏。
- 人事 `person` 采样能看到 `P001` / 张三。
- 办公账号 `account` 采样能看到 `login`、`is_contractor`。

勾选**只勾新表**：`recruit_sys.candidate`、`hr_sys.person`（`appointment` 可选）、`oa_sys.account`。
不要重勾第一波生成过的表。已裁过的类名对不会再出候选；被并掉的类会换成幸存者再出新对——只准跳过 / 仅名称相似。

### 3.2 唯一键与裁法顺序

| 对象（来源标签） | 唯一键对照的列 |
|---|---|
| 招聘 `candidate` | `id_no` |
| 人事 `person` | 先 `person_no`（给办公账号那一对），裁完部分重叠再改回 `id_no` |
| 办公账号 `account` | `person_no` |

顺序强制：**先**办公账号 × 员工部分重叠，**再**把员工唯一键改回 `id_no`，**再**候选人 × 员工阶段。
（反过来做：阶段合并后留下的类身份是 `id_no`，招聘源没有 `person_no` 列，账号那一对就再也对不上了。）

1. 员工与账号唯一键都对照 `person_no`，两边名称属性同名 `name`。「算一算」：命中 35，约 **70%**。
   点「部分重叠」。成功信号：多一个公共对象，账号的 `is_contractor` 还在账号上，`name` 挪去了公共对象。
2. 员工唯一键改回对照了 `id_no` 的字段；候选人唯一键已是 `id_no`。「算一算」：命中 30，约 **38%**。
3. **阶段**：候选人对象在乘号前、员工对象在后，不对就对调。早填 `candidate`、晚填 `employed`
   （输入框示例是设备那一组 `in_transit` / `in_service`，人的阶段卡要手改这两个词）。
4. 阶段之后新出的「账号 × 已合并人员」：跳过或仅名称相似。禁止同一 / 阶段。
5. 人 × 设备、任职 × 部门、候选人 × 账号（若出现）：仅名称相似或跳过。
   任职与部门用的是同一套 D01–D08 组织编码，名字像，但不是同一类东西。

### 3.3 发布与问题集关卡

发布 vN+1。合并人员类上应出现派生 `status`（`candidate` / `employed`）与动作 `convert_to_employed`
——这一波**不跑**这条动作（录用要补入职表单，超出简单转化，本期只问数不写库）。

「换成第二波问题」→「全量跑一遍」。换成时上一波的「在役设备一共多少台」应消失（换成会先清空再装入）。全绿才能进第三波。

| 问句 | 期望 | 含义 |
|---|---|---|
| 在职人员一共多少人 | `50` | 人事源有行（含 30 个两边都有身份证的） |
| 还停在候选人阶段、人事还没有行的人一共多少 | `50` | 招聘有、人事无 |
| 名叫张三的人员有多少 | `1` | 张三在 30 人交集里 |
| 身份证 11010119900101000X 且处于在职阶段的人员有多少 | `1` | 张三 |
| 身份证 11010119900101030X 且处于候选人阶段的人员有多少 | `1` | `C031`，人事没有这行 |

## 4. 第三波 · 客与货（4 个库，分次生成）

### 4.1 接入，分次生成

接入 `crm_sys` / `sales_sys` / `wms_sys` / `ar_sys`（toast 表数 1 / 2 / 1 / 1）。

**必须分次生成**（每次勾完点「生成对象」，等节点上画布再勾下一拨）：

1. `sales_sys.customer` + `sales_sys.order`
2. `crm_sys.customer`
3. `purchase_sys.order`（第一波故意没勾的那张办公采购）
4. `wms_sys.stock` + `ar_sys.invoice`

同一次生成两张同名表（两个 `customer`、两个 `order`）会被模型合成一个类——一个节点挂两个源，等于还没裁就已经「同一」，看见了就删掉重生成。
跨次撞名由平台自动处理：草稿里已有 `customer` 时，这一波生成的类名会是 `crm_sys_customer` 这种带连接前缀的名字——**认对象靠来源标签**。

成功信号：四个独立节点，来源标签分别是销售客户、客户档案、销售订单、采购办公订单、库存、发票各归各位；
没有任何节点同时挂两张 `order` 或两张 `customer`。

### 4.2 唯一键

| 对象（来源标签） | 唯一键对照的列 |
|---|---|
| 客户档案 `crm_sys.customer` | `customer_no`（`CUST-001`…`CUST-040`） |
| 销售客户 `sales_sys.customer` | `cust_no`（前 30 个与档案同号同名） |
| 销售订单 `sales_sys.order` | `order_no` |
| 采购办公订单 `purchase_sys.order` | `order_no` |
| 库存 `wms_sys.stock` | `sku` |
| 发票 `ar_sys.invoice` | `invoice_no` |

客户两类的名称属性如果同名 `name`，部分重叠会把 `name` 挪到公共对象上；不同名也能裁。

### 4.3 裁法

| 对（用来源标签认） | 结论 | 说明 |
|---|---|---|
| 客户档案 × 销售客户 | 部分重叠 | 「算一算」命中 30，**75%**。公共字段只有同名 `name`（编号是唯一键，不算公共）。别裁同一：同一之后并集 50，对错板会红 |
| `purchase_sys.order` × `sales_sys.order` | 仅名称相似 | 撞表名而已：一个买办公用品，一个卖产品。禁止同一（同一之后「销售订单」会变成 85 条） |
| 库存 × 销售订单 | 跳过或仅名称相似 | 库存不是订单，禁止同一 |
| 发票 × 销售订单 | 跳过或仅名称相似 | 发票的 `order_no` 对得上部分销售单，但它不是订单那一类 |

交集率的 30 是「对得上号」的条数，不是问数行数——问数看到的是单源 40。对错板不设期望 30 的客户题。

### 4.4 发布与问题集关卡

发布 vN+1。「换成第三波问题」→「全量跑一遍」。换成时第二波的「在职人员一共多少人」应消失。全绿 = 三波走查完成。

| 问句 | 期望 | 卡住什么 |
|---|---|---|
| 销售订单有多少条 | `60` | 采购办公订单被裁成同一 → 85 |
| 仓库里有多少种 sku | `30` | 库存被并进订单会红 |
| 应收发票有多少张 | `40` | — |
| 销售系统客户表里的客户有多少 | `40` | 与客户档案裁成同一后并集 50 |

## 6. 失败排查

| 步 | 该看见 | 不对时 |
|---|---|---|
| 播种 | 十二个绝对路径 + 连接表单字段 | 文件被开发服务占用：先停 `npm run dev` 再播种 |
| 连接 | toast 表数对得上 §1；列有注释；采样有行（资产「没有行」） | 查 `.ontos-demo/*.comments.json` 是否跟上；坏 sidecar 会在保存时被拦 |
| 生成 | 每张勾选表有来源标签；字段说明含注释；撞名类带 `连接名_表名` 前缀 | 原始产出在临时目录 `ontos-llm-fail/`；漏表就删掉草稿对象重生成 |
| 唯一键 | 抽屉里对应列不是「未映射」 | 模型没收列：重生成，不要手编映射 |
| 删 `status` | 设备类无非派生 `status`（阶段之前必须拿掉） | ✕ 被「仍被引用」拦（关系/公理/派生/动作引用；源对照不拦删除）：先解引用再删 |
| 交集率 | §5 的数字 | 点检 ≈22% = 拖到阶段之后了；对调后条数跟着类走 |
| 裁决 | toast + 节点合并；`shared_*` 多一个且原类还在 | 乘号反了：放弃回到上次发布（没检查点 = 空 v1，要重新生成），下次先对调 |
| 发布 | toast vN；对象卡出现派生 `status` 与 `convert_to_in_service` / `convert_to_employed` | 422 照校验文案改 |
| 问题集 | 期望数字装入即见；跑完题旁有明细 | 明细里找：枚举（`in_service` 不是「在役」）、类名、阶段名、limit、映射 |
| 动作 | `result.structuredContent.ok === true`，projections 有成功 insert | `stage: "pre"` = 前置不满足（该台不在在途）；看错信封顶层会以为没返回 |

## 7. 非目标

- 测试代码（vitest / Playwright）不代人点生成、裁决、发布——这条英雄路径就是给人走的。
  自动化只做离线门闩：默认 `npm test` 零出站（剥 `OPENAI_API_KEY` / `ONTOS_TOKEN`），钉种子数字与关卡逻辑。
- 不做步骤条 / 走查浮卡 / 页内问数与动作控制台 / Copilot；引导全部在已有卡片上。
- 不把十二个文件自动注册进任何空间；不改 `test` 空间的内存注入。
- 第二波不做「录用」写库动作（补全入职表单超出简单转化）。
- 生产槽位不设 `temperature: 0`；live 自检不进 CI。
- 问数行数不设「两库交集 30」这种期望：交集数是裁决面板的证据，不是查询结果。
