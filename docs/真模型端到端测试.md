# 真模型走查（一家公司 · 设备一生 + 办公线 · 八套接入系统）

这是 Ontos 的可演示走查剧本（ADR 0012）：同一家公司，一条设备主线（采购在途 → 台账在役 → 转固 → 维修 → 报废/处置）
+ 一条办公支线（办公设备 / IT 报修 / 门禁 / OA 部门 / 会议室 / 办公用品），两条线在「维修」处交汇。
操作者接源、勾表生成概念级对象（模型跨表归纳概念），在画布上审 Agent 的判定与整合、随手纠偏，人点发布、跑问题集；判定不设人工环节，结论与证据在留痕视图查看。
动作演示在画布外走 MCP。测试代码不代人做这些步骤（那是非目标，见文末）。

**走查必须配真模型三件套**（`OPENAI_API_KEY` / `OPENAI_BASE_URL` / `OPENAI_MODEL`）。不配也能起服务，
但演示实现只够证明「连得上、表在、列注释在」：候选对建议是通用启发式，问数剧本只覆盖 `test` 演示空间——
空白空间里的生成、判定建议、问题集跑批都必须走真模型。

**两套世界，数字不要混。** `test` 空间是附录 C 模板 + 七个内存 fixture（在役 **97** / 在途 81 / 报废 3），
给 `engine.test.ts` 钉数字用。走查在**新建空白空间**里进行，设备阶段世界只有两条规则：
在役 **97**（设备源 100 行，含 3 台台账 scrapped）、在途 **81**（采购 121 − 重合 40）。别拿别的数字来卡走查。

## 0. 准备

```bash
export OPENAI_API_KEY="…"
export OPENAI_BASE_URL="https://api.x.ai/v1"   # 或任何 OpenAI 兼容端点；填基址，SDK 自己拼 /chat/completions
export OPENAI_MODEL="…"                        # 必须显式
# 不要设 ONTOS_TOKEN：浏览器写请求配不上令牌会 401
npm run dev    # http://localhost:6688
```

另开终端，仓库根：

```bash
npm run demo:seed
```

该看见：十二个系统的清单——给人看的名字、连接名、类型「SQLite 文件（演示）」、绝对路径。
文件写在 `.ontos-demo/`（不进 git），重复运行整份覆盖。**验收动作之后再播种会丢掉刚写回的设备行。**

播种只写文件：不动元库、不替你连任何空间。连接由你在画布表单里逐套接。

浏览器里：左上角下拉 → 「新建工作空间」→ 起个名字（如 `lab`，小写字母开头）。
**不要用 `test`**（已发布附录 C + 内存七连，看不见「接入」这一关）；
**不要假设 `default` 是空的**（本机玩过就可能残留旧连接）——新建一个。

**认对象靠来源标签，不赌类名。** 画布节点标题是模型起的类名（可能是 `po_item` 也可能是 `purchase_item`）；
节点下方的来源标签是 `连接名.表名`（如 `device_sys.device`）。下文「采购对象」= 来源标签含 `purchase_sys.po_item` 的那个节点。
**模型偶尔会把类名起得出乎意料**（如办公设备叫 `it_sys_device`、IT 报修单叫 `repair_ticket`）——
对 Agent 下指令时点名来源标签（「把来源是 it_sys.device 的类改名叫 it_device」），Agent 自己认。

## 1. 十二套系统（数据源抽屉的答案）

点左下角「数据源」开抽屉接入。`npm run demo:seed` 的 stdout 打印十二行连接答案（给人看的名字、连接名、「SQLite 文件（演示）」、绝对路径），与下表对齐；下表另两列——表、接入后 toast 表数——是接入后的核对项，不在 stdout。左栏「可接入（演示文件）」按行点「接入」：连接名自动照清单来（来源标签靠它认对象），保存前先测连通，一次接一个库；MySQL / PG 或自选路径走左栏「手动接入」，照 stdout 的绝对路径填。接入成功 toast 的表数必须与下表一致。

| 波 | 给人看的名字 | 连接名 | 表 | 接入后 toast 表数 |
|---|---|---|---|---|
| 1 设备 | 采购系统 | `purchase_sys` | `po_item`、`order` | 2 |
| 1 设备 | 设备台账 | `device_sys` | `device`、`department`、`assignment` | 3 |
| 1 设备 | 资产系统 | `asset_sys` | `asset`、`warranty_card`、`disposal` | 3 |
| 1 设备 | 维修工单 | `repair_sys` | `repair` | 1 |
| 1 设备 | 点检系统 | `inspect_sys` | `instrument` | 1 |
| 2 办公 | IT 系统 | `it_sys` | `device`、`ticket` | 2 |
| 2 办公 | 门禁系统 | `access_sys` | `card_holder` | 1 |
| 2 办公 | 办公系统 | `oa_sys` | `account`、`dept`、`room`、`booking`、`supply`、`requisition` | 6 |
| 原料 | 客户档案 | `crm_sys` | `customer` | 1 |
| 原料 | 销售系统 | `sales_sys` | `customer`、`order` | 2 |
| 原料 | 仓库系统 | `wms_sys` | `stock` | 1 |
| 原料 | 应收发票 | `ar_sys` | `invoice` | 1 |

人事（hr_sys）与招聘（recruit_sys）已撤（ADR 0012）；客户/销售/仓库/应收四个客货系统保留为原料
（可连可不连，不进剧本、不产生候选对）。**办公系统的六张表一次全生成**——会议室、预订、用品、领用单
不参与对齐判定，是画布上的丰富性对象（预订/领用也是动作演示的落点）。

接入成功 toast：`已连接 <名字>，读到 N 张表`，右栏随即显示该源的表结构。生成在右栏做：勾选表 → 「生成对象」，草稿节点上画布、抽屉收起，下一批再点「数据源」开。抽屉里每张表：列名 / 类型 / 主键 / 列注释，
列下面是最多 3 行脱敏采样（空表写「没有行」）。列注释来自库文件旁边的 `.comments.json`
（拷库不拷它时按文件名回退种子注释；它坏了接入会被拦下并报错）。

若列注释缺失：停下来查 `.ontos-demo/<库>.comments.json` 是否存在，不要继续生成——字段说明会变差，唯一键更难认。

## 2. 第一波 · 设备一生（5 个库，概念归纳与并类）

### 2.1 接入，看抽屉

按 §1 接入 `purchase_sys` / `device_sys` / `asset_sys` / `repair_sys` / `inspect_sys`。抽屉里该看见：

- `purchase_sys.po_item`：列 `sn` 旁有「设备序列号」；采样能看到 `SN-4xxxx`（按插入顺序是 `SN-40000` 起，主角 `SN-40217` 是第 121 行，不要求出现在采样里）。
- `purchase_sys.order`：办公采购（打印纸、文具供应商），**没有**序列号——订单含条目（部分与整体），它的判定是跳过案。
- `device_sys.device`：列 `serial_no` 注释「设备序列号」、`status` 注释「台账状态」。**没有 `repair` 表**（维修独立成库了）。
- `device_sys.department`：车间口径（一车间、二车间……），与 OA 的部门表是第二波同形异义的那一对。
- `asset_sys.asset`：52 行（40 台生产设备转固 + 12 台办公设备转固）——不是空表，别当接错了。
- `asset_sys.disposal`：处置档案 8 条（3 台台账 scrapped + 5 台台账已移除）。
- `repair_sys.repair`：15 行工单，序列号来自在役设备；一条未结束。
- `inspect_sys.instrument`：60 行点检对象（40 台与设备台账重合）。

### 2.2 勾表生成（每库一次「生成对象」，模型归纳概念）

勾选范围：`po_item` 与 `order`（同库两张表一次勾，跳过案由 Agent 判）、`device`、`department`、`assignment`、`asset`、`disposal`、`warranty_card`（**单独勾**——凭证表，别和资产混在一批）、`repair`、`instrument`。

键由 Agent 建稿时定（数据试算 + 语义判别，结果落草稿），先分行：行是个体本身（或其时期）的取个体编号列——`po_item.sn` / `device.serial_no` / `asset.sn` / `instrument.serial_no` / `disposal.sn`（处置档案的行是设备的已处置时期，一一对应）；
行是记录或凭证的取自己的单号列——维修工单 `repair_no`、保修卡 `card_no`（卡身上的设备序列号是引用列，不做身份）。判定落定、人审画布后，「第一波」问题集应当全对：**在役 97 / 在途 81 / SN-40217 在途 1 / 维修工单 15**。

五对由 Agent 依证据判定（结论与证据在留痕视图查看，人审画布）：

| 候选对 | 判定与落地 | 证据 |
|---|---|---|
| 设备台账 `device` × 资产 `asset` | 同一概念：并成一个对象，台账、资产两个源都挂上 | 序列号重合 40 台；资产 52 行 = 生产 40 + 办公 12（办公那 12 台别被并进设备） |
| 点检 `instrument` × 设备台账 `device` | 同一概念：并入设备的多源类（点检 40 台对上，独有 20 台也是设备） | 点检 60 中 40 台对得上设备；点检独有 20 台 |
| 采购 `po_item` × 设备台账 `device` | 同一个体的不同时期：一个对象，时期派生（早 在途 / 晚 在役） | 重合 40 台是「同一台设备两个时期」；主角 `SN-40217` 只在采购源 |
| 处置 `disposal` × 设备台账 `device` | 同一个体的又一段时期：并进设备类，时期派生接上「已处置」 | 处置 8 行与设备一一对应（3 台台账 scrapped 也有处置记录，另有 5 台台账已移除）；行=个体的已处置时期，不是事件 |
| 订单 `order` × 采购条目 `po_item` | 跳过：这次不定 | 订单含条目（部分与整体），本期不定案——别判成同一概念；同库两张表也进判定 |

**台账状态列让位**：`device.status` 列（台账状态）与时期派生的 `status` 属性撞名——判定前 Agent 把它改名为 `mark`（台账标记），让派生时期接管 status。并类完成后设备类挂五个源（采购、台账、资产、点检、处置），时期三段：在途（只在采购源）/ 在役（台账有行）/ 已处置（处置档案有行）。

**并类的连带**：设备类并上资产、点检、处置源后，画布上不再有单独的资产、点检、处置类——后面凡是这些提法都指设备类里的对应来源（来源标签认）。

## 3. 第二波 · 办公线（3 个库，同形异义与关联建链）

接入 `it_sys` / `access_sys` / `oa_sys`，抽屉里该看见：

- `it_sys.device`：办公设备 40 台（电脑/显示器/打印机），`asset_tag` 是资产编号、`sn` 是设备序列号（前 12 台与资产表对得上——转固残留，不是同一概念的证据）。
- `it_sys.ticket`：IT 报修单 12 条（2 条未关闭）。
- `access_sys.card_holder`：门禁卡 45 张（35 张对得上办公账号，10 张是访客/已离职）。
- `oa_sys.account`：办公账号 40 个（35 正式 + 5 外包，`is_contractor` 列区分）。
- `oa_sys.dept`：行政组织 6 个部门（综合部、财务部……）——与设备台账的车间表是同一对同形异义的另一半。
- `oa_sys.room` / `booking` / `supply` / `requisition`：会议室 8 间、预订 20 条、用品 25 种、领用单 18 张。

勾选范围：全部 6 张 oa 表 + it 两表 + 门禁一表。第二波的键同样由 Agent 落草稿：`account.login` / `card_holder.card_no` / `it_sys.device.sn` / `ticket.ticket_no` / `oa_sys.dept.dept_id`——门禁卡的行是挂在人上的卡，键取自己的卡号 `card_no`；`holder` 是指向账号的引用列，不做身份，供建链配对（holder=login，谁的卡）——「门禁 35」靠的是这个配对。两处随手纠偏（画布编辑卡的活）：
`account.is_contractor` 列是 0/1 整数，让 Agent 把它改成枚举 `[0, 1]`（问数编译按枚举取值认 1/0）；
`it_sys.ticket` 的类描述带上「办公」字样（模型生成时常写成「设备报修工单」，与生产设备的维修工单混不开，跑「维修工单」问题会数错类）。判定由 Agent 依证据落定：

| 候选对 | 判定与落地 | 证据 |
|---|---|---|
| 生产设备 `device` × 办公设备 `it_sys.device` | 不是同一概念（同形异义）：两类留下，不连线 | 都叫 device、都有序列号，但生产设备与办公设备不是同一种东西；办公 12 台转固进资产是设备类资产源里的行，不影响这对 |
| 维修工单 `repair` × IT 报修单 `ticket` | 不是同一概念（同形异义）：两类留下，不连线 | 都叫「维修/报修」，一个管生产设备、一个管办公设备 |
| 台账车间 `department` × OA 部门 `dept` | 不是同一概念（同形异义）：两类留下，不连线 | **交集率 0%**（两套编码无交集）；都叫部门，台账按车间/产线、OA 按行政组织 |
| 办公账号 `account` × 门禁卡 `card_holder` | 不比同类：门禁卡是挂在账号上的卡——落法是建「谁的卡」链（`has_card`，login↔holder） | 35 张卡的 `holder` 对得上账号（正式都有卡）；外包 5 人没卡、访客 10 张对不上账号——holder 大面积命中恰好暴露它是引用列 |

事件与记录类（维修工单、履历、报修单）与主体表的对，Agent 一律不比同类、倾向同形异义——它们的归宿是与主体建链（引用列配对）。判定落定、人审画布后，「第二波」问题集应当全对：**门禁 35 / 外包 5 / IT 报修 12 / 办公设备 40**。

## 4. 第三波 · 保修与验收（建链 + 发布）

保修卡与设备的落法是建链：Agent 建 `covered_by`（设备被保修卡覆盖，inverse `covers`，靠序列号配对，卡身 `sn` 是指向设备的引用列）。「保修期内 20」靠这条链答——30 张卡里 20 张未过期；验收主角 SN-40217 的卡由验收动作现建（不在种子里）。

然后工具条「发布」把人审过的画布定稿成新版本（Agent 的判定与证据都已在留痕视图；发布由人点；预订/领用的发号规则与两个业务动作要在发布前由 Agent 落进草稿）。发布后跑「第三波」问题集应当全对：**处置档案 8 / 保修期内 20 / 采购订单 25 / 未结束维修 1**。

## 5. 验收动作（画布外走 MCP）

发布后由外部 Agent 经 MCP `run_action` 跑动作（动作定义在发布前由 Agent 落草稿；转化动作由时期判定自动立）：

- `convert_to_in_service`（验收入库）：`SN-40217` 从在途转在役；
- `convert_to_scrapped`（报废）：在役一台转已处置——**别拿 SN-40217 报废**，指定 `SN-40085`（报废它不影响「SN-40217 在役 1」）;
- `book_room`（预订会议室）：给 `R-01` 订一个上午时段；
- `request_supply`（领用办公用品）：领一箱打印纸。

跑完「验收后」问题集应当全对：**在役 97（+1 转固 −1 报废）/ 在途 80 / SN-40217 在役 1 / 预订 21**。

## 6. 不做的事（测试代码的边界）

上面的步骤里，人的部分在画布上做（选表、审画布、发布），Agent 的判定与整合自动跑；自动化测试只覆盖引擎层（engine.test.ts）与对错板数字（questions.test.ts）。
演示实现的问数剧本（`llm/demo.ts` 的 demoQueries）只服务 `test` 空间，走查里新建的空白空间不认它。
