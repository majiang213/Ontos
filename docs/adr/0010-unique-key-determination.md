# 唯一键判定：索引是证据不是规则，数据试算参与建议，Agent 落地草稿可回滚；复合键本期不支持

导入时模型/演示实现只靠表结构（列名、注释、主键、唯一约束）给唯一键建议；`propose_key` 是识别唯一键的第二步——按疑似重复候选对做数据试算（每源每列 ≤ 1000 行：逐源表内唯一性 + 候选键 × 候选键命中），再把试算结果喂给实现（`proposeKey` 出口）综合判断，出建议并标注硬/软保证，由 Agent 落 `set_identity`（草稿可回滚）；`propose_key` 开放给 Agent。

**索引是证据不是规则。** 唯一约束只证明单表内不重复（同一性标准三条里的「能区分」），证明不了覆盖（唯一列可空）、稳定、以及最要紧的跨源对得上号。所以唯一约束只当候选列的进门凭据之一，不当最终判定；最终判定 = 数据命中 + 实现语义判断 + 人确认。候选列四选一进门：当前建议 / 单列唯一约束 / 非整数主键 / 名称或注释带业务编号特征（仅非整数列，整数列不靠名字召回——自增代理键最常见的形态）。

**表内唯一性由数据说话，不靠索引语义推理。** 试算逐源检查「去重数 = 行数」：表内已重复的候选直接出局。复合唯一索引/复合主键的单列在表内重复，被数据天然挡掉——不用在索引解析里推理复合键（内省也只标单列唯一）。

**进门前先分行：行是个体本身（或其时期），还是关于个体的记录。** 个体的行（台账、采购条目、点检对象）的身份取个体编号列；记录的行（保修卡、工单）取自己的单号列——记录身上的他类编号列（如保修卡上的设备序列号）是引用，命中越多越证明它是引用，除名出局。

**命中是确认性证据，0 命中不否定。** 数据对上号强烈支持该候选；0 命中只说明没有数据佐证，不证明键错（两个类的个体可以天然没有交集），建议退回导入时的判断或留给人。软保证（仅数据验证、无唯一约束）可进建议，面板标注硬/软——create 动作幂等依赖源表唯一索引，软保证列当唯一键时幂等会退化，标注让人知情。

**试算上限 1000 行/列（KEY_TRIAL_SCAN）。** 识别是建议不是证据：千行采样能发现重复（发现即出局），不追求全局唯一证明；正式交集率（裁决证据）仍走 5 万行上限，两处不混。

**复合键本期不支持。** `identity` 是单列；真唯一键要两列合起来的表没有单列解，唯一键留空、不参与疑似重复、发布被拦（有源无键）。若这类表在真实数据里常见，另立 ADR 讨论复合键或拼接键概念，不为单场景新开配置键。
