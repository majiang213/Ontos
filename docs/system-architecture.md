# Ontos 系统架构

> 本文是产品与系统结构的唯一总览。它不维护配置键、查询请求或完整 YAML；这些内容统一见 [本体参考](ontology-reference.md)。领域概念统一见 [根目录 CONTEXT.md](../CONTEXT.md)，局部取舍见 [ADR](adr/)。

## 1. 产品边界

Ontos 是架在企业存量数据库上的本体中间层：从表结构归纳业务对象，按证据整合多源，再用已发布本体提供问数和受控动作。业务行始终留在原库，客户应用不需要改造；平台不另造一套业务库。

本期支持 MySQL、PostgreSQL 和 SQLite 文件作为源库，平台元数据可用 SQLite、MySQL 或 PostgreSQL 保存。对外主入口是 MCP，另有只读查询 REST 入口。

本期系统承载已发布本体上的问数和受控动作；本体元素、配置键和执行语义见[本体参考](ontology-reference.md)。子类型、部分与整体、不相交、规则推理、OWL、CDC、出码和新应用骨架不在本期范围内。

## 2. 一条完整链路

```text
接入源库
  → 读取表结构与脱敏采样
  → Agent 从表归纳对象草稿
  → Agent 按证据提出整合结果并写入可回滚工作副本
  → 人在画布上审查、纠偏并发布
  → 查询按已发布本体实时查源库
  → 动作按已发布定义校验后投影回源库
```

建模期的整合结果进入可回滚工作副本：候选快照写入 `adj_candidates`，交集证据写入 `adj_overlap`，最终裁决及其证据快照写入 `adj_decision`，都不进入本体配置；查询期只按已发布配置组装各源行。两层语义的规定见[本体参考](ontology-reference.md)。

### 人、Agent 和引擎的边界

- Agent 负责理解表结构、提出唯一键和整合草稿；引擎负责交集率、配置校验、查询求值和动作执行。
- Agent 的建议只写工作副本；人审画布并负责发布。发布、放弃和回滚不开放给 Agent。
- `propose_objects` 只建议，`edit_draft` 才修改工作副本；外部循环由调用方负责，Ontos 不内置 ReAct。
- 查询和动作只读已发布版本；未发布改动不会影响下游。

## 3. 模块和接口

| 模块 | 职责 |
|---|---|
| 连接器 | 连接 MySQL、PostgreSQL、SQLite 文件，读取表结构和脱敏采样；业务查询使用只读账号，动作可另配可写账号。 |
| 逆向建模 | 把勾选的表归纳为概念级对象；建议与落草稿分为 `propose_objects` 和 `edit_draft/import_objects`。 |
| 多源整合 | 召回疑似重复、计算交集率、提出或记录裁决；候选快照写 `adj_candidates`，交集证据写 `adj_overlap`，裁决写 `adj_decision`，都不是配置键。 |
| 本体管理 | 维护工作副本、画布状态、版本和发布；发布后的 YAML 是单一事实源。 |
| 查询服务 | 将结构化查询按已发布本体确定性编译，各源下推后在内存中组装结果。 |
| 动作执行器 | 解释已发布动作并投影原库；不接受自由 SQL，不为具体源系统写行业分支。 |
| 血缘与日志 | 提供属性到源列的取数路径，并分别记录查询 `log_query` 和动作 `log_action`。 |

对外能力收敛为两条：`query` 实时只读源库，`run_action` 执行已发布动作。建模、整合和画布编辑通过 MCP/REST 的边界工具完成，不另造一套 CRUD 应用。

## 4. 平台元库

平台只存元数据，不存业务行。交集计算在内存完成，标识值集合算完即弃；查询和动作日志保存请求摘要、版本、耗时和成败，不保存结果集。

当前元库按职责分为：

| 前缀 | 表 | 用途 |
|---|---|---|
| `conn_` | `conn_source` | 源库连接和权限信息。 |
| `onto_` | `onto_workspace`、`onto_version` | 工作空间注册、工作副本、画布和已发布版本。 |
| `ont_` | `ont_question` | 验收问题集及其运行状态。 |
| `adj_` | `adj_candidates`、`adj_overlap`、`adj_decision` | 分别保存候选快照、交集证据、最终裁决及其证据快照。 |
| `log_` | `log_query`、`log_action` | 问数和动作日志。 |

表结构的可执行事实以 `src/server/meta/ddl/sqlite.sql`、`mysql.sql`、`pg.sql` 为准；本文只说明职责和隔离关系，不复制 DDL。

## 5. 工作空间和版本

工作空间是隔离单位：一套本体配置、版本链、平台元数据和画布状态。共享元库用 `workspace_id` 隔离所有空间，所有元数据读写由 MetaStore 统一带上空间条件。

- `onto_version` 的编号行是已发布快照；`version IS NULL` 的唯一工作行是可变工作副本。
- 工作副本把本体、摆位、弯折和钉点放在同一个画布包中；发布复制成编号版本，不修改历史版本。
- 工作副本的 `rev` 用 CAS 保护并发编辑：`UPDATE ... WHERE rev = ?` 影响 0 行即为冲突；重启和多实例不会丢失修订号。
- 点历史版本会覆盖工作副本，但不会自动发布；问数仍读原已发布版本，确认后再点发布。
- 本地默认使用 SQLite；设置 `ONTOS_META_DSN=mysql://...` 或 `postgres://...` 切换共享元库。多实例部署使用 MySQL/PG，并为每个实例分配 `ONTOS_SNOWFLAKE_INSTANCE_ID`（0–1023）。
- `default` 和新建空间均为空白起步。`test` 空间首次注册时才播种演示模板和 fixture；演示空间的实例本地 fixture 不承诺多实例一致。

旧的“每个空间一个目录/一个 SQLite 文件”是迁移前形态，不再作为现行架构。

## 6. 数据边界和一致性

- 不迁移、不复制业务行；源库被外部修改时，下一次查询按源库当前状态读取，本期不做 CDC。
- 多源查询分别下推到源库，再在应用层按已发布配置的对齐键组装；这只描述问数取数，不等于类间对齐判定。
- 动作按效应和 `sources` 推出写回目标，不在动作里写表名；跨库不做分布式事务。
- 每条投影是源库上的短事务并带条件；部分失败记录到 `log_action`，补偿方式是幂等重发同一动作或人工修库。
- 发布是人对工作副本的最终确认，版本全量保存，历史版本可覆盖回工作副本后重新发布。

## 7. 当前范围和验收

当前是否可用，以代码、有效 ADR 和 [真模型端到端测试](真模型端到端测试.md) 为准。走查覆盖：接入数据源、生成对象、Agent 整合、人审画布、发布、问数、动作和验收问题集。

后续方向包括告知外发、凭据加密与权限细化、子类型、质量回归和更细的裁决自动化分级；它们是预留方向，不是本期已经交付的能力。
