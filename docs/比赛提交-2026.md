## 作品名称

## 作品链接

## 作品简介

同一台设备，在采购、台账、资产三个系统里是三个名字。它们是不是同一个？Ontos 把本体论工程化：机器可读的本体覆盖在现有数据库之上，规定什么存在、何时同一；交集率当证据，由人定案。接入只加配置不加代码，查询、写回都按本体执行。不搬一行数据，每一步有定义、有证据、可回滚。

## 作品详情（全体可见）

### 问题定义：什么存在、何时同一

人工智能在企业业务中的落地，以数据语义的一致理解为前提，跨系统同一性是最基础的环节：同一设备在采购、台账、资产三套系统中标识不同，采购记"在途"、台账记"在役"。是否为同一对象、是否为同一对象的先后时期，数据层本身不提供判定依据。数仓迁移只复制数据，语义留在人工维护；模型直连把语义判断交给模型临场推断，两条路线都不建立机器可读的语义定义。Ontos 以本体建立该定义：规定什么存在、何时同一，交集率当证据、由人裁决，查询与写回按本体执行。

### 背景与问题

| 问题 | 市面方案的现状 | Ontos 的做法 |
|---|---|---|
| 数据迁移成本高 | 数仓 / 指标平台先复制数据再人工建模，周期以季度计，源头一改全链路同步；API 集成每系统一套适配器，老系统常无开放接口 | 不搬数据：配置直连（只读账号连接、源映射、动作定义），新系统只加配置不加代码 |
| 模型直连风险高 | Text-to-SQL 与数据分析 Agent 由模型直接编译 SQL、自主多步查询；无语义定义，幻觉 SQL 无法前置拦截 | 模型只产结构化查询，引用的类/属性/关系必须在已发布本体中；SQL 由引擎确定性编译 |
| 跨系统同一性无依据 | 检索问答（RAG）检索文档与元数据，与实时数据脱节；跨库语义靠模型临场猜，回答无取数路径可核验 | 本体规定同一性，交集率当证据、由人裁决；查询实时下推各源，答案附取数路径 |

**Ontos 的相对优势**：

- 语义唯一出处：本体（YAML 单一事实源）规定类、属性、关系与同一性，版本化发布、可回滚——市面方案中语义或人工维护、或散落适配器、或临场推断；
- 模型不当计算器：模型只建议（对象草稿、候选对、结构化查询），编译与执行是确定性代码；
- 读写一体：查询联邦下推附取数路径，写回只执行已发布动作定义，配置即权限边界；
- 人把关合并：涉及合并的裁决（类等价 / 部分重叠 / 生命周期）只由人定案，裁决与证据留痕可回滚。

### 设计路线：配置直连，而不是 API 集成

| 路线 | 做法 | 语义定义在哪 | 代价 / 边界 |
|---|---|---|---|
| 数仓 / 主数据 | 复制数据、ETL 加工后再治理 | 人工维护（ETL 与文档） | 周期以季度计；源系统一改，全链路同步；数据存两份 |
| API 集成 | 每系统一套适配器 | 散落在各适配器代码 | 老系统常无开放接口；适配器随系统数线性增长；语义各写各的 |
| 模型直连 | 模型直接生成 SQL 执行 | 每次查询临场推断 | 幻觉 SQL 风险；语义无一致定义，同一问题答案可能不同；写库等于交出编辑权 |
| **Ontos 配置直连** | 连接（只读账号）+ 源映射（属性→列）+ 动作定义 | 已发布本体，单一事实源 | 新系统只加配置不加代码；权限用数据库账号控制；取数路径可解释可审计；语义随版本可回滚 |

Ontos 的配置直连包含三项配置：连接（只读账号）、源映射（属性→列）、动作定义。查询与动作的 SQL 由引擎按本体确定性编译、按映射投影、按方言归一，下推源库执行；新系统只加配置不加代码。

### 方案：本体作为读写中间层

本体是一份机器可读的 YAML 定义，规定领域的类、属性、关系与同一性标准；本体不含业务数据，个体（Individual）留在源库。它架在现有数据库之上，是查询与动作执行的语义依据：

- **类与属性**：「设备」类有名称、状态、所属部门等属性；「部门」类有名称、负责人等属性；
- **源映射**：每个属性挂到具体来源——「设备.名称」来自设备库 devices 表的 name 列、「设备.状态」来自采购库 purchase_orders 表的 status 列。一个类可挂多张表，一列也可喂多个类（多对多）；
- **个体留在源库**：本体只描述类与规则，不存业务行；每一行数据仍躺在原库原表，查询与动作直接读写它们。

覆盖在全部现有数据库之上，本体回答五个问题，这是融合的语义依据：

1. **什么存在**：本体定义类，个体留在源库（类与个体分离）。
2. **何时同一**：每个类先定唯一键；跨源识别以交集率当硬证据，由人裁决为类等价 / 部分重叠 / 生命周期 / 同形异义；模型建议只是软证据，裁决与证据快照留痕可回滚。
3. **变化中保持同一**：生命周期把同一体的先后时期（在途→在役→报废）建模为派生阶段字段，转化动作自动建立。
4. **同名与异实**：同形异义用于名字相似但指称不同的类（设备台账部门 vs OA 部门），结论写入配置，不产生合并。
5. **部分与整体**：本期不裁决（订单×条目、保修卡×设备），避免强行归类。

类等价、部分重叠、生命周期、同形异义、同一性标准均为本体论术语，在 Ontos 中落地为裁决动作与配置结构。

### 核心机制：先定义、后执行

读与写共用一条原则：本体先定义并发布，引擎才执行；模型只建议，SQL 由确定性代码生成。

- **查询（读）**：问题 → 结构化查询（只能引用已发布本体的类/属性/关系）→ 按源映射翻译成各源 SQL → 下推源库执行 → 按关系拼装 → 答案附取数路径；
- **动作（写）**：动作请求 → 核对已发布动作定义（前置/效应）→ 按效应与源映射投影到各源表列 → 校验并执行 → 返回结果与变更事件；
- **一致性**：查询与动作只读已发布快照；本体版本化发布，可回滚；
- **证据链**：模型建议（软证据）→ 交集率（硬证据）→ 人裁决（结论），涉及合并的裁决不开放给自动流程。

### 查询与动作：模型建议、引擎执行

**查询（读）**：

1. 提问「列出**在役设备**及其**所属部门**」；
2. 模型把它编译为结构化查询，只能引用已发布本体里的**类**、**属性**、**关系**——本体之外的表名、字段编不出来；
3. 引擎按**源映射**把查询翻译成 SQL，各源语法不同（MySQL / PostgreSQL / SQLite）由引擎适配，实时下推设备库、部门库执行；
4. 按「设备 → 所属部门」**关系**把结果拼成一张表，附取数路径（每步取了哪个源、哪张表），返回。

**动作（写）**：

1. 执行「验收入库」，点名某台**在途设备**（**个体**）；
2. 引擎读已发布动作定义——**前置**（设备存在且在途）、**效应**（**状态**改为在役；资产源新增一行；立保修卡）；配置之外的动作直接拒绝；
3. **前置**校验通过后，按**效应**与**源映射**把写入投影到各源表列，逐源执行；create 靠源表唯一索引幂等，重发不重复落行；
4. 返回执行结果与变更事件；再查询一次，这台**设备**的**阶段**已是「在役」。

机制要点：

- 模型不当计算器：只出结构化查询与建议，SQL 编译与动作执行是确定性代码；
- 写回目标由效应与来源映射推导，动作定义不写表名，换源不改动作；
- 同一性标准复用：跨源识别与查询对齐共用同一唯一键；
- 生命周期裁决自动立转化动作，复合变更建模为同一动作的多个效应，执行器不按行业写分支。

### 使用流程

demo（https://tabula-rasa-initiate.mynocode.host）即开即用：纯前端静态部署，浏览器内运行完整引擎与演示数据，无需部署、无需登录、无需模型 Key。打开后两个入口：

- **test 工作空间**（开箱即用）：7 个演示连接、15 个本体对象已就绪，6 对疑似重复待裁决，四波验收问题集可直接跑批；
- **空白工作空间**（从零走一遍）：从「连接数据源」开始，用演示数据完整走完生成、裁决、发布、查询。

平台内五步：

1. **连接数据源**：配置只读账号接入源库，读取表结构（类型/主键/注释 + 脱敏采样）。
2. **生成对象**：勾选表结构，模型建议业务对象与关系草稿上画布；建议只进草稿。
3. **裁决**：疑似重复对象进待确认面板（跨库或同库两张表）：先定唯一键、再算交集率，裁决为类等价 / 部分重叠 / 生命周期 / 同形异义，或跳过。
4. **发布**：对象、关系、动作与全部裁决合并为单一事实源，带版本号入库。
5. **查询**：验收问题集「全量跑一遍」/「对草稿跑一遍」，展示结构化查询、执行结果与取数路径。

**示例链路**：接入采购、设备、资产三个库后，「在途设备」×「在役设备」交集率约 1/3，裁为生命周期；设备 × 资产全重合，裁为类等价。发布后查询「列出在役设备及其所属部门」，从三库实时拼装并附取数路径；执行动作「验收入库」，写设备源、资产源各一行并立保修卡，阶段变为在役。

### 安全与治理

- 平台元库不存业务数据列；查询只读查源库，日志不存结果集；交集比对在内存完成，取值集合算完即弃；
- 写入仅执行已发布动作定义，配置之外被引擎拒绝；表结构采样脱敏后进入界面；
- 查询用只读账号、动作另备可写账号，写端点可加 Bearer 令牌；查询与动作全程留痕，裁决附证据快照，历史版本一键回滚。

| 框架 | Next.js 16 · React 19 · TypeScript | 前后端一体，画布、路由、引擎同仓 |

### 源项目运行

主库：`ssh://git@git.sankuai.com/~wb_liuxuhao02/ontos.git`（https://dev.sankuai.com/code/repo-detail/~wb_liuxuhao02/ontos/file/list）——含《Ontology平台MVP设计文档》、ADR 0011/0012（布局与演示剧本决策记录）、真模型端到端走查文档。

环境：Node.js ≥ 22.5。克隆主库后：

```bash
npm install
cp .env.example .env   # 全部可选：不配模型 Key 也能跑（走演示剧本）
npm run demo:seed      # 生成 12 套演示库（.ontos-demo/ 下的 SQLite 文件）
npm run dev            # http://localhost:6688
```

打开后进入 **test 工作空间**即开箱即用（7 个演示连接、15 个本体对象、6 对候选待裁决、四波问题集），与 demo 是同一套产品。连真实数据库（MySQL / PostgreSQL / SQLite）在「连接数据源」表单里配只读账号即可；配置 OpenAI 兼容模型 Key（`OPENAI_API_KEY` / `OPENAI_MODEL` / `OPENAI_BASE_URL`）后，真模型接管生成对象、候选对、查询编译等建议类功能。

外部 Agent 经 MCP 驱动：

- 端点：`POST http://localhost:6688/api/<空间名>/mcp`（JSON-RPC 2.0）；只读查询另有 REST 形态 `POST /api/<空间名>/query`；
- 配套 skill 在仓库 `skills/` 下四个目录：ontos-query（查询）、ontos-action-run（执行动作）、ontos-canvas（读写画布）、ontos-action（动作定义）；
- 人的关卡（选表、唯一键、裁决、发布）不开放给自动流程。

验证：`npm test`（Vitest，462 项：结构守门 / 纯度边界 / 确定性全覆盖，套件剥离模型 Key、不连外网）。
