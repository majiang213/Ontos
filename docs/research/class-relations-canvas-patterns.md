# 复杂类关系的呈现：官方产品资料核对与 Ontos 设计候选

> 设计阶段研究记录，不是现行产品规格。本文不修改概念定义、裁决记录形状或本体配置；现行口径以 `CONTEXT.md`、有效 ADR 和代码为准。候选方案仍待设计阶段确认。

- 研究日期：2026-10-11。
- 方法：读取产品官方文档、官方仓库和产品作者的一手论文，核对界面承载的信息及交互边界。没有登录这些产品实测；没有分析 RelShow 测试样本。
- 范围：Protégé / WebProtégé、WebVOWL、Neo4j Bloom、Linkurious Enterprise、Enterprise Architect、Figma 的对照交互。它们的对象与任务不同，不能把图探索能力等同于本体判定能力。

## ① 研究结论

本轮没有找到一个已核产品，直接提供 Ontos 所需的完整组合：对同一被比对的两个类，同时呈现分类含义、来源个体覆盖、时期语义、判定依据，并保持这些信息与个体之间的业务边相区别。这是本轮核对范围的结论，不是对整个市场的否定。

能借鉴的是几种互补的呈现办法：

| 产品案例 | 实际承载的信息 | 可借鉴的办法 | 不能据此声称的能力 |
|---|---|---|---|
| Protégé / WebProtégé | OWL 类、公理、属性、个体及修改记录 | 分类分区、每条陈述独立显示、声明与推理结果区别 | 自动比较数据库来源覆盖，或直接采用 Ontos 的类等价定义 |
| WebVOWL | OWL 本体结构的图形表示 | 主图配详情、按表达内容过滤、平行属性曲线 | 自动产生来源覆盖或时期判定 |
| Neo4j Bloom | 图数据库中的节点、关系和属性 | 专项视图、局部展开、关系折叠后可查看组成 | OWL 类关系推理，或把布局中的上下位置当作子类型 |
| Linkurious Enterprise | 图数据库的业务数据及其连接 | 同类型同方向平行边聚合、表与图联动 | 把不同语义的关系聚合成同一个结论 |
| Enterprise Architect | 建模元素之间已存在的连接 | 按类型筛选的关系矩阵、单格回到明确元素 | 为未建模的两个元素自动判定关系 |
| Figma | 设计对象、版本、图层和属性差异 | 从画布进入专项对照、差异列表定位详情 | 类关系表达或本体推理 |

**对 Ontos 的设计推断**：普通画布、类配对总览、单项依据明细可以承担不同的问题。不能因为各项都能画成线，就要求它们在同一张图中一直同时出现；也不能因为界面设了过滤项，就把类关系定义成封闭枚举。

## ② 产品逐项核对

### 1. Protégé / WebProtégé：陈述分区，不把类的描述压成一个标签

**官方事实**：Protégé 的 Class Description 按 `EquivalentTo`、`SubClassOf`、`DisjointWith` 等分区呈现选中类的公理，每行对应一条公理；`Instances` 列出个体归属。不同分区可以共同描述一个类，但这不意味着任意两条互相矛盾的公理都成立。推理得到的信息可在相应分区显示，与直接声明的信息有区别。[Class Description](https://protegeproject.github.io/protege/views/class-description/)

**官方事实**：Class Hierarchy 默认显示声明的子类结构，可以切换到推理出的结构；从 5.5 起可选择展示基于对象属性公理的其他关系，悬浮提示给出属性名及完整关系的文字说明。因此树也是一种选定规则的投影，不是类关系的全貌。[Class Hierarchy](https://protegeproject.github.io/protege/views/class-hierarchy/)

**官方事实**：WebProtégé 的官方指南描述了选中实体的 OWL 描述浏览器，公理注解以缩进形式展示，并提供实体修改记录与版本快照。官方仓库确认其 OWL 2 编辑、变更历史及可定制界面能力；本轮没有核实 WebProtégé 与桌面版在推理展示上的功能一致性。[WebProtégé User Guide](https://protegewiki.stanford.edu/wiki/WebProtegeUsersGuide)、[官方仓库](https://github.com/protegeproject/webprotege)

**边界**：OWL `EquivalentClasses` 不能直接替换 Ontos 对分类含义与来源覆盖的区分。公理注解、修改记录也不等于数据库交集率证据。本轮未核对到这些产品原生提供按源表计算覆盖交集或判定 Ontos 时期语义的界面。

**对 Ontos 的推断**：借鉴“明确的陈述分区 + 每条陈述能展开依据”，不照搬 OWL 术语。分类含义与来源覆盖可以同时呈现；时期另写清描述的是谁的不同时期。每项保留自己的来源与时间，不能用一枚裁决芯片代表类的全部含义。

### 2. WebVOWL：结构图与明细分担信息，图上的线仍须读清语义

**一手论文事实**：作者将 VOWL 2 的重点放在类、属性和数据类型；个体详情在联动的详情区域显示。类之间的属性线主要对应属性的定义域和值域，不是一次实际发生的个体业务关系。等价类可合画为一个双圈节点；同两个类之间的多个属性采用曲线避开重叠。[Visualizing ontologies with VOWL，§3、§4、§5](https://journals.sagepub.com/doi/10.3233/SW-150200)

**一手论文事实**：WebVOWL 提供内容过滤及按节点连接数缩减图的控件；论文所述界面默认把不相交信息放在详情区域，可选择画入图中。论文也说明大型本体呈现存在限制。[同一论文，§4.2.4、§6](https://journals.sagepub.com/doi/10.3233/SW-150200)

**版本边界**：上述具体行为取自产品作者的 2015/2016 年论文，是经过描述的成熟交互先例，不能冒充本轮最新版本实测。官方发布记录后来包含 WebVOWL Editor，因而不能拿早期“仅可视化”的公告断言现在完全不能编辑。官方仓库还明确旧 `visualdataweb.org` 域名已不归项目所有，新入口是 TIB 服务。[官方仓库](https://github.com/VisualDataWeb/WebVOWL)、[发布记录](https://github.com/VisualDataWeb/WebVOWL/releases)、[当前服务入口](https://service.tib.eu/webvowl/)

**对 Ontos 的推断**：可借鉴按信息内容选择显示、文字明细保留依据、平行线独立定位。不要按节点连接数筛掉“重要性较低”的类判定：连接少的类仍可能存在必须审查的判定。也不要为了画得紧凑，把尚待人审的两个类仅在视觉上合成一个节点。

### 3. Neo4j Bloom：同一数据的专项视图与局部探索

**官方事实**：Perspective 为一个图定义业务查看范围，可配置实体类别、属性可见性、关系可见性与样式；同一图可有多个 Perspective。这是显示和探索上下文，不是复制一套数据库。[Perspectives](https://neo4j.com/docs/aura/explore/explore-perspectives/perspectives/)

**官方事实**：Scene 只包含经搜索或探索取得的部分图。用户可沿指定关系类型及方向展开邻居，查看 Inspector，过滤当前内容。相同两个节点间的多条关系可折叠，显示数量；展开检查可看到组成的关系类型。层次布局按数据库中关系的方向安排节点，并不证明存在分类继承。[Overview](https://neo4j.com/docs/bloom-user-guide/current/bloom-visual-tour/bloom-overview/)、[Scene interactions](https://neo4j.com/docs/bloom-user-guide/current/bloom-visual-tour/bloom-scene-interactions/)

**边界**：这些说明针对图数据库中的节点与连接。没有据此核实 OWL 公理判定、来源覆盖比较或类关系推理。折叠多条边只能说明有若干现存连接，不能替代各连接的语义。

**对 Ontos 的推断**：可在同一画布主页面增加专项查看模式，按当前问题决定突出哪些已有内容。显示“已隐藏什么”及返回原视野的入口，避免把没显示的项误读成不存在；展开邻居只增加查看范围，不产生新的判定。

### 4. Linkurious Enterprise：聚合有明确边界，明细与图保持联动

**官方事实**：Edge Grouping 针对同类型、同方向的平行边；组标签给出边数，选择组可查看类型、数量与聚合属性。它不是把任意不同含义的边合成一条。[Edge Grouping，4.3.13](https://doc.linkurious.com/user-manual/latest/edgegrouping/)

**官方事实**：节点和边分别有过滤列表，当前过滤条件可以查看、删除和重置。选择多个节点或边时，属性面板以表格展示；不同节点类别或边类型各有表格。表格条目可定位图上的对应项。Selective Expand 可限定类别、边类型和取回邻居数量。[Filter panel](https://doc.linkurious.com/user-manual/latest/filter-panel/)、[Inspect data](https://doc.linkurious.com/user-manual/latest/visualization-inspect/)、[Expand nodes](https://doc.linkurious.com/user-manual/latest/expand/)

**边界**：表格中的数据、边属性及聚合结果来自现有图数据，本轮没有核对到来源对齐判定证据的专用形状，也没有核对到本体逻辑推理能力。

**对 Ontos 的推断**：一条类配对条目可展开多个独立陈述，各自点开自己的依据。总览上的“若干项待查看”只能作为入口；不能把分类含义与来源覆盖求和或平均。平行业务链仍要能逐条选择，聚合范围必须明示。

### 5. Enterprise Architect：关系矩阵回答整体连接覆盖，详情回答具体关系

**官方事实**：Relationship Matrix 以表格显示模型元素之间的连接，可按 Perspective、模型元素类型、连接类型、方向及包筛选。格子里的箭头表示相应连接及其方向；选中格子会突出两个元素的名字。界面要求选择所查看的连接类型，也可查看或编辑关系属性。[Relationship Matrix，17.2](https://www.sparxsystems.com/enterprise_architect_user_guide/17.2/the_application_desktop/elementrelationshipmatrix.html)

**边界**：矩阵显示模型中已有连接，本轮核实的页面没有提供“一个格子同时完整说明不同维度类关系及其依据”的能力。元素可以是类，也可以是其他建模元素；这不是 OWL 推理结果矩阵。

**对 Ontos 的推断**：类配对表或矩阵适合回答“哪些类已被比较、哪些项有依据”，不适合在格子里塞整段证据。没有记录的格子只能表示“当前范围没有可显示记录”，不能表示 Agent 已判定不相交。完整矩阵会产生大量空格及滚动成本，可以先用有记录的类配对表；是否升级为矩阵应由真实规模与查阅任务决定。

### 6. Figma：画布上的选择可以进入更充分的专项对照

**官方事实**：Dev Mode 的 Compare changes 从选中 frame/component 进入，可比较历史版本、实例与基础组件，也可选择两个组件比较。专用对照同时提供并排与叠加视图、变更图层列表和属性差异；选择图层会定位对照画面。官方也描述从 Focus view 进入版本对照。[Compare changes in Dev Mode](https://help.figma.com/hc/en-us/articles/15023193382935-Compare-changes-in-Dev-Mode)

**边界**：Figma 比较设计资产和版本，既不表达类关系，也不判断个体集合的重合。叠加像素图不能挪作分类含义或来源覆盖的证据。

**对 Ontos 的推断**：借鉴“主画布负责选择，专项对照提供足够阅读面积，条目与对象相互定位”。详情应直接写两个类的名字、来源和字段，不靠界面方位称呼比较对象。

## ③ Ontos 应先分清的显示内容

以下是本仓库约束及设计推断，不是外部产品事实：

| 要显示的问题 | 当前可读依据 | 显示约束 |
|---|---|---|
| 两个类描述什么；Agent 当时对什么作了判定 | 类定义、裁决结论及证据快照 | 分类含义与来源覆盖分区；没记录的结论不能由界面补出 |
| 当前类挂着哪些来源、比较时得到什么覆盖证据 | `sources`、交集证据、裁决保存的证据快照 | 源映射本身不说明个体覆盖；不展示标识集合或业务行，历史试算不能冒充当前实时覆盖 |
| 同一个体的不同时期怎样表达 | 时期属性、派生规定、转化关系及动作 | 与个体之间的领域业务边区分，不重新立阶段类 |
| 不同概念的个体如何关联 | 已有 `link_types` 中的领域谓词 `match` 链 | 线标签说明业务含义；不能把它解释成分类关系 |
| 过去比较过什么、现在结构变成什么 | 裁决历史与当前工作副本分别读取 | 合并后当前只剩一个多源类；原先两个类属于历史比较对象 |

依据：[CONTEXT.md「类与类」「判定与证据」](../../CONTEXT.md)、[ADR 0013 的最终决定](../adr/0013-partial-overlap-lands-as-link.md)。CONTEXT 明确分类含义上的类等价与来源覆盖上的部分重叠可以同时成立；当前同概念合并的规定没有因此改变。

**记录形状的限制**：当前 `DecisionRec` 每条保存一个 `verdict`；画布判定条目主要取得被比较的类及该次结论，详细依据另有读取。多条历史裁决不能自动解释为同一时刻同时成立的多项当前陈述。若后续要求按独立维度同时保存和维护结论，需要先设计事实记录及有效性规则；本研究不增设配置键，不臆造缺失依据。[当前裁决记录类型](../../src/server/meta/types.ts)、[判定词汇与执行计划](../../src/server/schema/verdict.ts)

**历史对照的限制**：当前裁决入口保存的证据包括计数、交集率、统一格式规则和匹配字段，没有完整的类定义快照。类合并或删除后，仅靠裁决记录不能恢复它当时的全部定义、来源和字段。历史详情应展示实际保存的内容；若需要完整的原类对照，须另行确认是否存在可用的版本快照及其对应关系。[裁决请求形状](../../src/server/schema/request.ts)、[裁决记录写入](../../src/server/features/integrate/decide.ts)

**平行线的代码检查**：当前普通边按节点矩形、钉点、障碍和手工弯折计算路径，没有按同两个节点间的其他边自动分配不同路径。因此，同向业务链在几何输入相同时会取得相同路径，标签也有重叠风险。这是代码阅读所得，尚未用浏览器复现场景；后续若设计平行链呈现，应单独验证。[FloatingEdge](../../src/components/canvas/FloatingEdge.tsx)、[画布边投影](../../src/components/canvas/OntologyCanvas.tsx)

**推断规则的限制**：显示 A 与 B、A 与 C 的已有记录，不能仅凭连通或邻近位置补出 B 与 C 的关系。不同陈述拥有不同语义，是否可推导必须另有明确规则及依据；本轮候选均只读取已经存在的事实。

## ④ 候选呈现方案及代价

这几项是交互方案的比较，不是类关系的枚举。专项模式与固定面板可以组合；本研究不替设计阶段最终定案。

| 候选 | 适用任务 | 代价与风险 | 与当前约束的关系 |
|---|---|---|---|
| 独立关系查看页 | 大规模配对总览、长时间批量审查、复杂矩阵 | 需要在结构画布与关系记录之间反复跳转；选择、当前版本及对象消失的状态要跨页保持 | 增加独立导航页与单画布约定冲突，本轮不作为新增页面建议；它的大面积阅读收益可用主页面内专项模式取得 |
| 画布内专项查看模式 | 在结构与类对照之间切换；从总览定位单项 | 需要清楚提示正在看什么、哪些内容被隐藏；退出要恢复视野；不能因切模式改卡位置或改本体 | 保留单画布；可在模式中显示类配对表，选记录后聚焦对象并展开依据 |
| 固定对照面板 | 从画布选两个类或一条记录，逐项阅读依据 | 常驻会挤占画布；多条长证据需要独立滚动；很难独自提供整体关系覆盖 | 保留单画布；适合承担单项详情，可按需打开，并与专项总览联动 |

**待确认组合**：普通结构视图继续展示本体对象、业务链和时期；“类对照”专项查看模式提供有记录的类配对总览；选条目后，在可收起的对照面板中分别显示分类含义、来源覆盖、时期及其已有依据。它综合借鉴 Protégé 的分区、Bloom 的专项视图、Linkurious 的表图联动与 EA 的配对总览；不是任何一家产品的完整照搬。

该组合只消费已有事实。当前没有独立维度结论时，展示那次判定实际说了什么及保存的依据，不强行填满每个分区。人对 Agent 的纠偏仍通过既有对话，不恢复固定单选判定面板；发布仍由人完成。

已约束的返回行为应保留：对照只读；关闭恢复原视野，卡位置不变；对象改名时当前提示随名称更新，历史保留当时名称；删除或合并对象时移除相应当前提示并关闭失效对照，裁决历史继续保留。这些是会话确认的行为，不是本轮新确认的整体界面方案。

## ⑤ 设计阶段继续确认的问题

- 用户主要是在找“两个类有什么关系”，还是在复核“Agent 为什么这样改了草稿”？前者需要现行事实的有效性规则，后者可以围绕裁决及当时依据组织。界面必须让用户分辨这两个任务。
- 合并后的详情主要是“一个类的多源覆盖”，还是“合并前两个类的历史对照”？两者都可能有价值，但不能用同一标题让用户误以为两个类现在仍存在。
- 总览是否要包括尚未比较的两个类？若包括，空项必须说明没有记录，不能暗示 Agent 已判定不相交；若不包括，界面须说明总览范围。
- 分类含义、来源覆盖、时期是否需要各自维护当前结论？若需要，先完成独立事实与依据记录的设计，再讨论同时显示哪些结论。界面不会修复单条记录表达能力的限制。
- 同两个类之间有多条业务链时，是独立曲线、折叠入口还是条目选择？选择哪种都应保留各条业务谓词与方向，不能仅靠颜色区别。
