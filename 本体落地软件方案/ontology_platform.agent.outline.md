# 通用 Ontology 平台：产品与技术架构设计

## 1. 为什么是现在：Ontology 的复兴与 AI 落地的鸿沟（约 1200 字）
### 1.1 企业 AI 落地的真实瓶颈
#### 1.1.1 大模型能力过剩与企业数据"不可理解"之间的矛盾：LLM 直接对接数据库与 API 时缺乏业务上下文、权限约束与可审计性
#### 1.1.2 数据孤岛与系统林立：企业平均运行数十上百个业务系统，数据只有 IT 懂、业务看不懂
### 1.2 Ontology 从学术概念到产业基础设施
#### 1.2.1 Palantir 将 Ontology 定义为"组织的运营层/数字孪生"，包含语义元素与动力元素[^1^]，并以其支撑 AIP 实现受治理的 AI 决策[^9^]
#### 1.2.2 微软 Fabric IQ（预览）跟进本体方向，印证"本体层"正在成为下一代企业数据栈的标准组件[^12^]
### 1.3 本文档目标与读者
#### 1.3.1 定义一个通用 Ontology 平台的产品形态、元模型、技术架构与落地路径，覆盖"数据建模"与"现有系统改造"两类需求

## 2. 产品定位与核心价值（约 1500 字，1 表）
### 2.1 一句话定位
#### 2.1.1 AI 时代的本体底座：让企业用业务语言建模整个组织，让数据、应用与 AI Agent 在同一语义层上协同
### 2.2 通用的正确含义：元模型通用 + 模板垂直
#### 2.2.1 平台只内建"对象、属性、关系、动作、规则、接口、权限"七个元概念，行业语义全部通过模板与实例化承载
#### 2.2.2 行业模板市场作为冷启动与网络效应引擎，避免"什么都能做、什么都不好用"的通用平台陷阱
### 2.3 三类核心价值（表：价值—痛点—对应能力）
#### 2.3.1 对数据团队：语义统一与低成本系统改造，数据可不搬家
#### 2.3.2 对业务团队：用业务对象直接提问与操作，决策闭环而非只看报表
#### 2.3.3 对 AI 应用：Agent 经本体获得上下文、权限与工具，告别幻觉与越权（dbt 基准显示 Agent 走语义层准确率近 100%[^13^]）
### 2.4 不是什么：与数据中台、知识图谱、BI 的边界划分

## 3. 竞品格局与市场空白（约 1800 字，2 表）
### 3.1 国际阵营
#### 3.1.1 Palantir Foundry：能力最完整（对象+关系+Action+函数+AIP），但封闭、昂贵、数据须迁入索引[^15^]
#### 3.1.2 Microsoft Fabric IQ：方向正确（本体+Operations Agent 受治理行动）但处预览期且锁微软生态[^12^]
#### 3.1.3 语义层三杰 dbt/Cube/AtScale：只读指标语义供 Agent 消费，无对象关系模型与 Action[^13^][^21^]
#### 3.1.4 知识图谱系 Stardog/Neo4j/Ontotext/TopQuadrant：强存储与推理，无业务写回与 Agent 原生消费[^14^][^22^]
### 3.2 国内阵营
#### 3.2.1 知识图谱厂商（明略、海致星图、星环 Sophon KG）：停留在图谱构建与分析，无 Action 概念[^16^]
#### 3.2.2 云厂商图谱服务与 DataWorks 逆向建模：回应了存量系统改造需求但产出是数仓模型而非本体[^17^][^18^]
### 3.3 市场空白：四能力交集无人覆盖（表：能力×厂商矩阵）
#### 3.3.1 通用本体建模 + 存量系统映射 + Action 写回 + Agent 原生消费 = 定位锚点
#### 3.3.2 国产化与私有化部署是额外机会窗口

## 4. 元模型设计：平台的灵魂（约 2000 字，2 表）
### 4.1 语义元素
#### 4.1.1 对象类型（Object Type）：业务实体/事件的模式定义，类比 Dataset→Object Type、Row→Object[^2^]
#### 4.1.2 属性（Property）：类型系统、单位、约束、敏感级别标记
#### 4.1.3 关系（Link Type）：基数、方向、语义化命名，支撑图遍历
#### 4.1.4 接口（Interface）：形状与能力的多态抽象，支撑模板复用[^1^]
### 4.2 动力元素
#### 4.2.1 动作（Action Type）：对对象/属性/关系的一组事务性变更，含参数、校验规则、副作用与写回[^3^]
#### 4.2.2 函数（Function）：服务端逻辑，读写本体的代码能力（TypeScript/Python 沙箱）[^4^]
#### 4.2.3 规则（Rule）：约束、派生属性与自动化触发条件
### 4.3 治理元素
#### 4.3.1 两层权限模型：schema 资源层 + 数据层（到具体属性值）[^5^]
#### 4.3.2 版本管理与 Ontology-as-Code：YAML 定义、Git 化、diff/回滚/CI——对标 Palantir 建模依赖 UI、API 只读的短板形成差异化[^10^]
### 4.4 决策四要素框架
#### 4.4.1 Data + Logic + Action + Security 构成一个运营决策，支撑决策血缘自动捕获[^7^]

## 5. 总体技术架构（约 1500 字，1 架构图说明 + 1 表）
### 5.1 五层架构总览
#### 5.1.1 数据层（客户现有系统）→ 映射层 → 本体层 → 行动层 → 应用/Agent 层
### 5.2 关键设计决策（表：决策—选项—理由）
#### 5.2.1 存储：图库（NebulaGraph）与关系库混合，本体定义与实例分离
#### 5.2.2 数据接入双模：虚拟化（查询下推，参考 OBDA/Stardog[^14^]）与物化（CDC 索引，参考 Palantir Funnel[^6^]）
#### 5.2.3 API 形态：由本体自动生成 GraphQL（参考 Hasura/PostGraphile 的权限内即时 API[^20^]）
#### 5.2.4 复用开源生态压缩自研成本：Airbyte/Singer 连接器[^19^]、MetricFlow 指标语义
### 5.3 部署形态
#### 5.3.1 SaaS 多租户 + 私有化单机/集群，面向国产化的信创适配

## 6. 子系统一：建模工作台 Studio（约 1500 字，1 表）
### 6.1 可视化建模体验
#### 6.1.1 拖拽式对象/关系/继承建模，图谱可视化预览，多人协作与版本历史（参考 WebProtégé 协作模式[^23^]）
### 6.2 AI 建模助手：核心差异化
#### 6.2.1 输入数据库 schema/Excel/接口文档/业务描述文本，LLM 自动生成本体草稿，人工确认修正
#### 6.2.2 对标 Palantir FDE 人肉实施模式：把建模成本从月级压到天级
### 6.3 模板市场
#### 6.3.1 行业模板（制造 ISA-95、零售会员、金融风控）发布、复用与二次创作机制
### 6.4 Ontology-as-Code
#### 6.4.1 模型 YAML 双向同步，Git 管理、代码评审、环境迁移（开发→生产）

## 7. 子系统二：连接与映射引擎 Connect——改造现有系统（约 1800 字，2 表）
### 7.1 连接器框架
#### 7.1.1 插件式架构复用 Airbyte/Singer 生态[^19^]：数据库、ERP/CRM、Excel、API、消息队列
### 7.2 语义映射三模式（表：模式—机制—适用场景—侵入性）
#### 7.2.1 虚拟映射：数据留在源系统，本体做语义视图，查询时下推，适合快速试点
#### 7.2.2 同步物化：CDC 实时同步入本体存储，适合跨系统联合查询与图计算[^6^]
#### 7.2.3 本体原生：新对象直接持久化于本体，支撑新建系统与老系统渐进退役
### 7.3 AI 辅助映射
#### 7.3.1 Schema 自动发现 + LLM 建议映射（表→对象、列→属性、外键→关系），人工确认
#### 7.3.2 逆向建模：从存量系统反推本体草稿，对标 DataWorks 逆向建模但产出为本体而非数仓表[^17^]
### 7.4 改造实施方法论
#### 7.4.1 四周试点路径：选域—映射—验证—上线 Agent 入口，不动存量系统

## 8. 子系统三：本体运行时 Runtime（约 1500 字，1 表）
### 8.1 查询服务
#### 8.1.1 由本体自动生成 GraphQL/REST API：对象 CRUD、图遍历、聚合；行级/列级权限内嵌[^20^]
### 8.2 Action 引擎：与知识图谱划清界限的命门
#### 8.2.1 Action 定义、参数校验、权限检查、写回源系统、副作用（通知/webhook/工作流）[^3^]
#### 8.2.2 事务与补偿：写回失败的回滚与对账机制
### 8.3 权限与审计
#### 8.3.1 对象/属性/Action 三级粒度；Agent 与人类用户走同一权限通道（AI 只能做你被授权做的事）[^5^]
#### 8.3.2 全量审计日志与决策血缘
### 8.4 开发者接口
#### 8.4.1 多语言 SDK（TS/Python/Java）与 MCP Server：让外部 Agent 安全消费本体[^10^][^11^]

## 9. 子系统四：Agent 层——本体之上的 AI（约 1500 字，1 表）
### 9.1 三类 Agent 角色（表：角色—能力—依赖模块）
#### 9.1.1 建模 Agent：schema/文档→本体草稿与映射建议
#### 9.1.2 查询 Agent：自然语言问数，本体约束下的图查询生成，权限内执行
#### 9.1.3 行动 Agent：自然语言→Action 调用，含确认、审批与审计（参考 AIP Logic 的 LLM 编辑本体机制[^9^]）
### 9.2 Agent 可靠性的本体根基
#### 9.2.1 本体提供实体消歧、可用工具清单、权限边界与审计轨迹，系统性抑制幻觉与越权[^13^]
### 9.3 人机协同决策闭环
#### 9.3.1 建议—确认—执行—审计四步模型；决策血缘记录"谁（人/AI）因何数据做了什么"[^7^]

## 10. MVP 路线图与演进（约 1200 字，1 表）
### 10.1 V1 验证链路与范围裁剪
#### 10.1.1 单链路：连接数据库→AI 生成本体草稿→人工确认→自动生成 API+问数 Agent；Action、模板市场后置
### 10.2 V2/V3 演进
#### 10.2.1 V2 加 Action 写回与私有化；V3 加模板市场、多租户与生态
### 10.3 商业化路径
#### 10.3.1 通用引擎 + 1-2 个行业标杆案例破局，模板驱动横向扩张；开源核心 + 企业版的选项分析

## 11. 风险与应对（约 1000 字，1 表）
### 11.1 产品风险
#### 11.1.1 通用平台冷启动悖论：客户买的是问题解决而非平台，须以行业模板破局
#### 11.1.2 沦为"又一个知识图谱"：Action 与 Agent 叙事必须守住
### 11.2 技术与交付风险
#### 11.2.1 映射复杂度爆炸、写回一致性、LLM 建模质量的兜底（人工确认不可省）
### 11.3 竞争风险
#### 11.3.1 巨头跟进（微软 Fabric IQ 预览期是窗口[^12^]）与大模型厂商下沉语义层的挤压

## 12. 结语（约 500 字）
### 12.1 平台宣言
#### 12.1.1 让每一家企业都能用业务语言描述自己，并让 AI 安全地在这个描述之上工作
